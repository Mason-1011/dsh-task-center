# dsh-task-center-task-reaper

**用途一句话**:任务接缝的存活面——持有任务的会话死了,自动释放持有,卡死的任务不再需要人工 `/task release`。

## 两个确定信号,零猜测

判"会话死了"不用超时启发式(挂机三小时的活会话会被误杀),只用两个**结构性确定**的信号:

| 信号 | 覆盖场景 | 动作 |
|---|---|---|
| `session/disposed` 事件 | 会话正常结束/被处置时仍持有任务(最常见的泄漏:窗口关了、会话结束但没提交) | 立即释放 |
| 挂载时清扫 | 进程崩溃重启:账本里的持有者在新的空会话库中必然不存在 | 全部释放 |

释放只作用于 `active`/`blocked` 状态的持有;`review` 状态不动(工作已完成,等人类验收,`approve`/`reject` 仍可用)。释放以 `system` actor 写域事件——归属诚实、无会话回执(没有会话可写)。contextPack 保留,下一个认领者带着全部记忆续做。

## 权限:状态机钉死

`system` actor 在 fold 里被钉死为**只许 `release`**(权限矩阵的机械列):progress/approve 等一概 `TASK_FORBIDDEN`。同理 `wake` actor 被钉死为只许 wake-set/wake-clear,approve/reject 收紧为仅人类——机械执行器永远不会变成第二个"能干活的身份"。存活判断本身(谁死了)发生在本插件里,在账本之外——账本只记录结果。

## 依赖与顺序

`inject: tasks, sessions, agentLoop`。注入 `agentLoop` 只为顺序:它的启动会创建配置代理(进会话库),保证清扫跑在这些持有者存在之后,不会误读刚要启动的会话。

## Known Limitations and Deferred Work

- **单进程部署假设**:多进程共享同一存储目录时,后启动进程的清扫会释放其他进程的活持有(跨设备/跨进程需要 P2 的远程存储携带真实存活信号)。
- 清扫与处置竞态由 CAS 兜底:修订号过期即放弃本次,下一个信号重试。
- 会话处置事件的监听失败只记日志(事件层已包含);清扫失败同样只记日志,下次挂载重扫。
